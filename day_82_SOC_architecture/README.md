# Security Operations Center (SOC) Architecture

## 1. Architecture Overview

A Security Operations Center (SOC) collects, processes, stores, correlates, and presents security telemetry from an organization's information systems.

Its architecture provides a continuous mechanism for transforming individual technical observations into actionable security intelligence.

A SOC must support several distinct operational responsibilities:

- Collecting security telemetry from distributed infrastructure.
- Normalizing events generated by different technologies.
- Maintaining reliable and searchable event storage.
- Detecting suspicious activity through correlation.
- Generating and managing security alerts.
- Presenting operational information through dashboards.
- Supporting investigation, escalation, and incident resolution.

The architecture implemented in the five source files follows this processing model:

    Security Data Sources
             |
             v
       Event Collectors
             |
             v
        Raw Events
             |
             v
      Parsing and Validation
             |
             v
     Normalized Security Events
             |
             v
        Event Storage
             |
             v
      Correlation Engine
             |
             v
       Security Alerts
             |
             v
     Analyst Investigation
             |
             v
      SOC Dashboards

Each component has a separate responsibility. This separation allows collection, normalization, storage, detection, and reporting to evolve independently.

## 2. SOC Architecture Components

### 2.1 Data Sources

Data sources are the systems and devices that generate security-relevant information.

They provide the original observations used by the SOC.

| Data source | Security information | Example events |
|---|---|---|
| Firewalls | Network traffic and access decisions | Connection allowed, connection denied |
| IDS/IPS | Network attack indicators | Port scanning, exploit attempt |
| EDR | Endpoint activity | Malware detection, process execution |
| Antivirus | Malware and file inspection | File quarantine, signature detection |
| Identity systems | Authentication and authorization | Login success, login failure |
| Active Directory | Directory and account activity | Account modification, privilege assignment |
| DNS servers | Domain resolution activity | Suspicious domain lookup |
| Web servers | Application and HTTP activity | Authentication failure, unusual request |
| Cloud platforms | Cloud control-plane activity | IAM changes, unusual API calls |
| Database servers | Database access activity | Privilege changes, unusual queries |
| Email systems | Email security activity | Phishing detection, malicious attachment |
| VPN gateways | Remote access activity | Connection establishment, authentication failure |

Data sources can produce different formats, timestamps, event structures, and levels of detail.

A SOC therefore requires a common event-processing model.

The implementations distinguish a source from an individual event.

A source has:

- Unique identifier.
- Name.
- Source type.
- Deployment environment.
- Operational status.

An event contains information generated by that source.

**Important distinction:** A data source generates security information. It does not necessarily collect, normalize, correlate, or investigate that information.

### 2.2 Data Collectors

Collectors transport security information from data sources into the SOC processing environment.

They provide the ingestion boundary between distributed systems and centralized security monitoring.

Common collection mechanisms include:

| Collection method | Mechanism | Typical application |
|---|---|---|
| Syslog | Message-based log transmission | Firewalls and network devices |
| Agents | Software installed on monitored systems | Endpoint telemetry |
| APIs | Authenticated requests to external services | Cloud and SaaS audit logs |
| File ingestion | Reading exported log files | Legacy infrastructure |
| Database connectors | Scheduled database extraction | Enterprise applications |
| Event streaming | Continuous message delivery | High-volume telemetry |
| Network listeners | Receiving network messages | Infrastructure monitoring |

Collectors should implement:

- Source identification.
- Authentication where supported.
- Input validation.
- Payload-size restrictions.
- Buffer management.
- Error handling.
- Delivery monitoring.
- Retry and recovery mechanisms.
- Operational health reporting.

#### Buffer management

A collector may receive events faster than the downstream processing system can consume them.

A buffer temporarily stores incoming events.

For example:

    Incoming events: 10,000 events/second
    Processing capacity: 7,000 events/second

    Backlog growth: 3,000 events/second

If this imbalance continues, the buffer eventually reaches capacity.

The implementations demonstrate bounded buffers and dropped-event counters.

A production collector should also support durable queues, backpressure, retry policies, and dead-letter handling.

**Backpressure** is the mechanism through which a downstream component communicates that it cannot currently accept more incoming work.

### 2.3 Event Parsing and Normalization

Different security products describe similar activities using different field names and formats.

For example:

| Source | Original field | Normalized field |
|---|---|---|
| Firewall | `src_ip` | `source_ip` |
| EDR | `device_name` | `hostname` |
| Identity provider | `principal` | `username` |
| Application | `eventTime` | `timestamp` |
| Cloud audit | `operation` | `event_type` |

Parsing extracts structured information from an incoming payload.

Normalization transforms that information into a consistent event representation.

The implementations use a common event structure containing:

| Field | Purpose |
|---|---|
| `event_id` | Unique event identifier |
| `source_id` | Originating data source |
| `timestamp` | Time when the activity occurred |
| `category` | Security event classification |
| `severity` | Event importance |
| `event_type` | Specific activity |
| `source_ip` | Originating IP address |
| `destination_ip` | Target IP address |
| `username` | Associated account |
| `hostname` | Associated device |
| `message` | Human-readable event description |
| `attributes` | Additional source-specific information |

The implementations use five event categories:

- Authentication
- Network
- Endpoint
- Application
- Cloud

They also use four severity levels:

- LOW
- MEDIUM
- HIGH
- CRITICAL

Severity and category represent different dimensions.

Category describes the nature of an event. Severity describes its assigned importance.

A network event can be LOW or CRITICAL depending on its characteristics and context.

#### Parsing validation

Normalization must reject malformed or incomplete events.

Examples include:

- Missing timestamps.
- Invalid IP addresses.
- Unsupported event categories.
- Unknown severity values.
- Empty event types.
- Incorrect JSON structures.
- Excessively large payloads.

Timestamps should be timezone-aware.

Without timezone information, events originating from geographically distributed systems can be ordered incorrectly.

#### Raw events versus normalized events

These are different representations.

| Raw event | Normalized event |
|---|---|
| Original source payload | Standardized event structure |
| Preserves source-specific fields | Uses consistent field names |
| Useful for parsing investigations | Useful for correlation and queries |
| May contain inconsistent formats | Uses validated data types |
| Suitable for audit retention | Suitable for operational analysis |

The PostgreSQL implementation stores raw payloads in JSONB and normalized events in a separate relational table.

This separation preserves original evidence while supporting efficient analytical queries.

## 3. SOC Event Storage

Event storage maintains the security information required for monitoring, investigation, correlation, and reporting.

A SOC may use multiple storage technologies depending on volume, query requirements, retention periods, and operational constraints.

| Storage approach | Primary purpose |
|---|---|
| Relational databases | Structured records and relationships |
| Search-oriented storage | Rapid event investigation |
| Object storage | Long-term raw log retention |
| Time-series storage | Time-based operational measurements |
| Data warehouses | Historical analytics and reporting |
| Distributed event stores | High-volume ingestion and retrieval |

### 3.1 Storage requirements

An effective event-storage architecture should provide:

- Durable persistence.
- Time-based retrieval.
- Source-based retrieval.
- User-based investigation.
- Severity filtering.
- Category filtering.
- Event deduplication.
- Indexing.
- Retention management.
- Access control.
- Auditability.

### 3.2 Event indexing

Indexes reduce the amount of data examined during queries.

The Python implementation maintains dictionaries indexed by source and username.

The JavaScript implementation uses `Map` objects.

The C++ implementation uses `unordered_map`.

The Java implementation uses hash-based collections.

The PostgreSQL implementation uses B-tree and GIN indexes.

Representative database indexes include:

| Index | Query supported |
|---|---|
| Timestamp | Latest events |
| Source and timestamp | Events from a particular source |
| Severity and timestamp | High-priority event retrieval |
| Category and timestamp | Category-specific investigation |
| Username and timestamp | User activity analysis |
| Source IP | Investigation of suspicious addresses |
| JSONB GIN | Queries on additional event attributes |

Index selection should reflect actual query patterns.

Excessive indexing increases storage requirements and write overhead.

### 3.3 Event deduplication

The same event may arrive multiple times because of network retries, collector restarts, or message-delivery behavior.

Deduplication prevents repeated processing of identical records.

The implementations derive deterministic identifiers from the source and payload.

For database-backed systems, unique constraints protect event identity.

Deduplication must be designed carefully.

Two genuinely separate security activities can have identical-looking payloads if the event identity does not include sufficient distinguishing information.

Production implementations should use source-provided event identifiers or carefully defined composite identities whenever possible.

## 4. Security Event Correlation

Correlation identifies relationships between multiple security events.

An individual event may be harmless or inconclusive.

A sequence of related events can indicate suspicious activity.

For example:

    10:00:00  Login failure from 203.0.113.45
    10:00:20  Login failure from 203.0.113.45
    10:00:40  Login failure from 203.0.113.45
    10:01:00  Login failure from 203.0.113.45
    10:01:20  Login failure from 203.0.113.45
    10:01:40  Login failure from 203.0.113.45

These observations may indicate a brute-force authentication attempt.

### 4.1 Correlation rules

A correlation rule defines the conditions under which related events generate a detection.

A rule generally contains:

| Parameter | Meaning |
|---|---|
| Rule identifier | Unique rule reference |
| Event category | Relevant event classification |
| Event type | Specific activity being monitored |
| Threshold | Minimum matching event count |
| Time window | Maximum permitted observation period |
| Grouping fields | Attributes used to associate events |
| Alert severity | Severity assigned to the resulting detection |
| Enabled status | Whether the rule is operational |

The demonstration implements the following rule:

| Parameter | Value |
|---|---|
| Rule | AUTH-001 |
| Category | AUTHENTICATION |
| Event type | LOGIN_FAILURE |
| Threshold | 5 |
| Time window | 5 minutes |
| Grouping fields | Source IP and username |
| Alert severity | HIGH |

The detection groups authentication failures by source IP and username.

Five or more matching events within the configured window generate an alert.

### 4.2 Time-window correlation

A time window prevents unrelated historical events from being combined indefinitely.

For example:

- Five failures within two minutes may indicate an attack.
- Five failures spread across several days may represent ordinary user activity.

The Python, JavaScript, C++, and Java implementations use sorted event sequences and sliding-window evaluation.

The general algorithm is:

1. Group events using the configured attributes.
2. Sort each group by event timestamp.
3. Maintain a left boundary.
4. Advance the right boundary through the event sequence.
5. Remove events outside the configured time window.
6. Evaluate the remaining event count.
7. Generate an alert when the threshold is satisfied.

For \(n\) events within one group:

- Sorting requires \(O(n \log n)\).
- Sliding-window evaluation requires \(O(n)\).
- Total complexity is \(O(n \log n)\).

The correlation algorithm is efficient for moderate event batches.

Large-scale SOC deployments should use incremental processing, event-time windows, distributed state management, and carefully designed retention of correlation state.

### 4.3 Different detection mechanisms

Not every detection requires multiple events.

Two important detection patterns are:

**Threshold-based correlation**

Detects repeated or aggregated activity.

Examples:

- Multiple failed logins.
- Repeated connection attempts.
- Excessive account modifications.
- Repeated access-denied events.

**Single-event detection**

Detects an event that independently satisfies a critical condition.

Examples:

- Confirmed malware detection.
- Critical security policy violation.
- Unauthorized privileged operation.
- High-confidence endpoint detection.

The implementations treat critical events separately from the multi-event brute-force rule.

### 4.4 Correlation limitations

Threshold correlation is not sufficient for every security scenario.

Its limitations include:

- Distributed attacks using multiple source addresses.
- Attacks that deliberately remain below thresholds.
- Delayed event delivery.
- Incorrect source timestamps.
- Missing user or IP attributes.
- Legitimate activity that resembles malicious behavior.
- Events arriving out of chronological order.

More advanced detection systems require behavioral baselines, entity relationships, threat intelligence, sequence-based detection, and contextual risk evaluation.

## 5. Security Alerts and Analyst Workflow

An alert represents a detection requiring investigation or operational attention.

An alert is not identical to an individual event.

A single alert can reference multiple supporting events.

The implementations maintain the relationship through event identifiers and alert-evidence collections.

### 5.1 Alert information

An alert includes:

- Alert identifier.
- Detection rule.
- Title.
- Severity.
- Description.
- Supporting event identifiers.
- Creation timestamp.
- Current status.
- Assigned analyst.

### 5.2 Alert lifecycle

The demonstration models three principal operational states.

    OPEN
      |
      v
    INVESTIGATING
      |
      v
    RESOLVED

Additional permitted transitions include:

    OPEN -> RESOLVED

    INVESTIGATING -> OPEN

    INVESTIGATING -> RESOLVED

    RESOLVED -> OPEN

The PostgreSQL model also includes a CLOSED state.

State transitions are validated rather than allowing arbitrary status changes.

### 5.3 Analyst responsibilities

SOC analysts use alerts to investigate suspicious activity.

Typical investigation activities include:

- Reviewing supporting events.
- Identifying affected systems.
- Examining source and destination addresses.
- Checking associated user accounts.
- Comparing activity across data sources.
- Establishing the incident timeline.
- Recording findings.
- Assigning severity and escalation.
- Documenting resolution.

The Java implementation includes an analyst service that handles alert assignment, investigation, and resolution.

The SQL implementation records alert status transitions in an audit table.

Production deployments should additionally maintain role-based authorization, evidence integrity, investigation notes, escalation records, and incident-response procedures.

## 6. SOC Dashboards and Reporting

Dashboards provide operational visibility into the SOC.

They aggregate event, ingestion, detection, and investigation information.

A dashboard should distinguish between infrastructure health and security detection results.

### 6.1 Event monitoring metrics

| Metric | Purpose |
|---|---|
| Total events | Measures event volume |
| Events by source | Identifies contributing systems |
| Events by category | Shows the distribution of telemetry |
| Events by severity | Highlights event importance |
| Events per time interval | Identifies unusual volume changes |
| Duplicate events | Measures repeated delivery |
| Invalid events | Indicates parsing and validation problems |

### 6.2 Collector health metrics

| Metric | Purpose |
|---|---|
| Active collectors | Measures operational availability |
| Last heartbeat | Identifies stale collectors |
| Events received | Measures ingestion activity |
| Events dropped | Identifies delivery failures |
| Queue depth | Measures processing backlog |
| Processing latency | Measures ingestion performance |

A SOC dashboard should not interpret the absence of alerts as evidence that the environment is secure.

A collector failure can produce an apparently quiet dashboard while preventing security events from reaching the detection system.

### 6.3 Detection metrics

Useful detection metrics include:

- Total alerts.
- Open alerts.
- Investigating alerts.
- Resolved alerts.
- Alerts by severity.
- Alerts by detection rule.
- Alerts by source.
- Average time to acknowledge.
- Average time to investigate.
- Average time to resolve.

The SQL implementation provides reusable views for event summaries, source health, alert evidence, and operational reporting.

The other implementations construct dashboard snapshots from their respective in-memory stores.

## 7. Relationships Between SOC Components

The components form a dependent processing chain.

| Component | Input | Output | Primary responsibility |
|---|---|---|---|
| Data source | System activity | Original telemetry | Generate security information |
| Collector | Original telemetry | Raw event | Transport information |
| Parser | Raw event | Structured fields | Extract information |
| Normalizer | Parsed fields | Standard event | Establish a common representation |
| Storage | Normalized event | Persisted record | Preserve and retrieve telemetry |
| Correlation engine | Related events | Detection | Identify suspicious patterns |
| Alert manager | Detection | Security alert | Maintain investigation state |
| Analyst workflow | Security alert | Investigation result | Support human investigation |
| Dashboard | Events, alerts, collector metrics | Visual reports | Provide operational visibility |

These responsibilities are related but not interchangeable.

A collector does not perform the same function as a parser.

A parser does not determine whether an event represents an attack.

A correlation engine does not replace event storage.

A dashboard does not replace investigation or incident response.

## 10. Data Integrity, Security, and Operational Controls

A SOC processes security-sensitive information. Its architecture must protect the information throughout ingestion, processing, storage, and investigation.

### 10.1 Data integrity

Important controls include:

- Deterministic event identification.
- Duplicate detection.
- Raw event retention.
- Database constraints.
- Event-to-alert evidence relationships.
- Auditable alert transitions.
- Consistent timestamp handling.

The SQL implementation enforces relationships through foreign keys and unique constraints.

The application implementations validate event structures before accepting normalized records.

### 10.2 Access control

A production SOC should implement role-based access control.

Representative roles include:

| Role | Typical responsibility |
|---|---|
| SOC Administrator | System configuration |
| Security Engineer | Detection engineering |
| SOC Analyst L1 | Initial alert investigation |
| SOC Analyst L2 | Detailed investigation |
| Incident Responder | Incident containment and response |
| Security Manager | Oversight and reporting |
| Auditor | Read-only governance review |

Authorization should be enforced at the application and database layers.

Access to raw logs, investigation evidence, and sensitive identity information should be restricted according to operational requirements.

### 10.3 Secure ingestion

Collectors should use:

- Authenticated connections.
- TLS encryption.
- Source identity verification.
- Input-size restrictions.
- Strict payload validation.
- Rate limiting.
- Controlled retry behavior.
- Audit logging.

Untrusted event attributes must not be interpreted as executable instructions.

Database queries should use parameterized statements rather than dynamically concatenated user input.

### 10.4 Sensitive information

Security logs may contain usernames, IP addresses, device identifiers, and other sensitive information.

Appropriate controls include:

- Data minimization.
- Retention limits.
- Encryption at rest.
- Encryption in transit.
- Restricted access.
- Audit trails.
- Secure backups.
- Controlled data exports.

The sample implementations demonstrate structural validation, but they do not implement a complete production security boundary.

## 11. Performance and Scalability

SOC architecture must account for continuously increasing event volumes.

A system that processes a small demonstration dataset may not remain efficient at enterprise scale.

### 11.1 Ingestion throughput

Throughput measures the number of events accepted or processed per unit of time.

A basic measurement is:

\[
\text{Throughput} =
\frac{\text{Processed Events}}{\text{Elapsed Seconds}}
\]

A production deployment should separately measure:

- Incoming event rate.
- Accepted event rate.
- Normalization rate.
- Persistence rate.
- Correlation evaluation rate.
- Alert generation rate.

### 11.2 Processing latency

Latency measures the time required for an event to travel through the processing pipeline.

\[
L_{\text{total}} =
L_{\text{collection}} +
L_{\text{parsing}} +
L_{\text{storage}} +
L_{\text{correlation}}
\]

A SOC should monitor end-to-end latency and individual processing stages.

Delayed event processing can reduce the effectiveness of time-sensitive detection rules.

### 11.3 Horizontal scaling

Horizontal scaling distributes workload across multiple processing instances.

A possible architecture is:

    Security Sources
           |
           v
    Distributed Collectors
           |
           v
    Durable Message Queue
           |
           v
    Parallel Normalization Workers
           |
           v
    Distributed Event Storage
           |
           v
    Correlation Processing
           |
           v
    Alert Management
           |
           v
    Dashboard Services

This architecture reduces dependence on a single collector or processing instance.

Distributed systems require additional mechanisms for:

- Partition assignment.
- Ordering guarantees.
- Duplicate delivery.
- Retry handling.
- Distributed correlation state.
- Failure recovery.
- Consumer coordination.
- Backpressure.

### 11.4 Database scalability

For high-volume SOC storage, useful approaches include:

- Time-based table partitioning.
- Partition pruning.
- Retention policies.
- Selective indexing.
- Batch insertion.
- Materialized reporting views.
- Read replicas.
- Archival storage.
- Query-plan analysis.

Indexes should be selected according to measured workload rather than added indiscriminately.

| Failure | Potential consequence | Required control |
|---|---|---|

| Collector failure | Ingestion interruption | Heartbeats and recovery |

| Invalid payload | Normalization failure | Validation and rejection records |

The implementations demonstrate selected failure conditions, including invalid payloads, unknown sources, duplicate events, capacity limits, and invalid alert transitions.

## 13. Practical SOC Processing Scenario

Consider an enterprise environment containing:

- A perimeter firewall.
- An endpoint detection platform.
- An identity management system.
- A cloud audit service.
- A centralized SOC monitoring platform.

An employee account receives repeated failed login attempts.

The processing sequence is:

**Stage 1: Data generation**

The identity system generates authentication failure events.

**Stage 2: Collection**

A collector retrieves or receives the authentication records.

**Stage 3: Raw ingestion**

The incoming payloads are stored in their original form.

**Stage 4: Normalization**

The parser extracts the timestamp, source IP, username, category, severity, and event type.

**Stage 5: Storage**

The normalized records become searchable security events.

**Stage 6: Correlation**

The detection engine groups failed authentication events by source IP and username.

**Stage 7: Alert generation**

Five or more matching failures within the configured five-minute interval generate a HIGH-severity alert.

**Stage 8: Analyst investigation**

The SOC analyst examines the supporting events, account activity, source address, and related endpoint information.

**Stage 9: Resolution**

The analyst records findings and updates the alert status.

**Stage 10: Dashboard reporting**

The dashboard reflects the new alert, its severity, its evidence count, and its investigation state.

This scenario demonstrates how separate SOC components cooperate to transform distributed security telemetry into an operational detection.

## 14. Limitations of the Implementations

These implementations are executable architectural demonstrations, not complete commercial SOC or SIEM platforms.

| Capability | Demonstrated | Production extension |
|---|---|---|
| Source registration | Yes | Centralized asset inventory |
| Event collection | Yes | Durable distributed collectors |
| Payload validation | Yes | Source-specific validation schemas |
| Normalization | Yes | Versioned normalization contracts |
| Event storage | Yes | Distributed durable storage |
| Deduplication | Yes | Distributed idempotency management |
| Threshold correlation | Yes | Stateful distributed detection |
| Critical-event detection | Yes | Context-aware detection policies |
| Alert management | Yes | Full incident management |
| Analyst assignment | Yes | Enterprise identity integration |
| Dashboard metrics | Yes | Interactive visualization |
| Access control | Partial | Complete RBAC and ABAC |
| Encryption | Not implemented | TLS and encryption at rest |
| Threat intelligence | Not implemented | Enrichment and reputation services |
| Machine-learning detection | Not implemented | Validated behavioral analytics |
| Automated response | Not implemented | Controlled SOAR workflows |
| Long-term retention | Not implemented | Archival and lifecycle policies |
| High availability | Not implemented | Replication and failover |
| Distributed correlation | Not implemented | Stateful stream processing |

The Python, JavaScript, C++, and Java programs use in-memory storage.

The PostgreSQL script provides durable relational storage structures and database-side processing examples.

The Java parser uses a defined pipe-delimited event representation, whereas the Python and JavaScript implementations use JSON payloads.

The C++ implementation receives validated structured event objects rather than implementing a complete JSON transport parser.

These differences are intentional implementation choices.

### PostgreSQL

Execute the SQL script against a PostgreSQL database using an account with permission to create schemas, tables, functions, and triggers.

The script creates sample sources, collectors, raw events, normalized events, correlation policies, alerts, evidence records, reporting views, and analyst workflow records.

The database script uses the `pgcrypto` extension's cryptographic functions and UUID-generation functionality. Ensure the extension is installed and available to the executing database role before running the script.

The intentional invalid-transition demonstration near the end of the SQL script is designed to raise a trigger exception. Execute that section separately within a savepoint-aware client if testing the failure path; a PostgreSQL transaction that receives an unhandled statement error must be rolled back to a valid savepoint before further statements can execute.
